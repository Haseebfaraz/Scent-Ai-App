# Phase 1 Audit — JS → Python FastAPI Migration

> **Architecture update**: the Python backend now lives in its own standalone repository
> (`dua-scent-ai-python`, deployed as its own Render service) rather than inside this repo's
> `python_backend/`. This repository is the **read-only behavioral reference** for that port —
> algorithms, scoring, Prisma schema, tests. The `python_backend/` directory below is the working
> prototype everything was originally built and verified in before the move; it may still be
> useful for side-by-side comparison during the move but is no longer the canonical location. See
> the new repo's `docs/MIGRATION_AUDIT.md` for the up-to-date file map and parity table.

Business model is fixed: **blend-builder / custom Hybrid-Tribrid-Quadbrid creation from real catalog components**, not catalog recommendation. Not revisited here.

## 1. Stays in Node/React

- `app/shopify.server.js` — Shopify auth/session (`PrismaSessionStorage`), scopes, app distribution.
- React Router frontend/admin pages, Theme App Extension (`extensions/chat-bubble/`).
- `app/routes/apps.scent-library.fragrance-preview.jsx` — signed App Proxy, preview UI, Save Build/Add to Cart/Recreate actions.
- `app/routes/api.save-build.jsx` — ratio-edit → Shopify variant reuse/create (Admin GraphQL, price-per-position math against `note_composition` metafield). Stays Node because it *is* Shopify product logic, not fragrance intelligence.
- `app/services/fragranceBuild.server.js` — Shopify Admin GraphQL: `productCreate`, `productCreateMedia`, `publishablePublish`, `productVariantsBulkUpdate`. Stays Node.
- Prisma — remains responsible for Shopify/session tables (`Session`, `CustomerToken`, `CodeVerifier`) and existing migrations.

## 2. Moves to Python

All deterministic fragrance logic, recommendation/scoring, profile/order-history/catalog services, Odoo integration, and OpenAI conversation orchestration — per the target architecture. Node keeps only the Shopify-specific adapter (auth, GraphQL product/variant creation, preview page, save-build).

## 4. Database ownership

No schema changes in this phase. Both Node (Prisma) and Python (SQLAlchemy models mirroring the same tables) point at the same `DATABASE_URL` Postgres instance. Real Prisma relations exist only for `Message→Conversation`, `RecommendationInventoryComponent→Snapshot→FragranceRecommendation` (cascade deletes); everything else (`conversationId`, `fragranceProductId`, `normalizedProductName`, etc.) is a logical string/UUID match, not an enforced FK — SQLAlchemy models should mirror this exactly (plain columns, not `ForeignKey`, except those three relations) so nothing silently becomes stricter than production data allows.

Tables Python needs models for: `Conversation`, `Message`, `CustomerProfileState`, `CustomerAccountUrls`, `Note`, `OrderHistory` (936k+ rows — read-mostly), `FragranceProduct`, `OdooOilMapping`, `ExistingCombination`, `ProductRegionSummary` (precomputed; do not derive live), `FragranceRecommendation`, `RecommendationInventorySnapshot`, `RecommendationInventoryComponent`. Session/auth tables (`Session`, `CustomerToken`, `CodeVerifier`) stay Prisma/Node-owned; Python doesn't need models for those in phase 1.

## 5. API boundary (Node ↔ FastAPI)

Simplest first cut: Node's `app/routes/chat.jsx` becomes a thin proxy. It keeps the existing CORS-open `/chat` contract (`GET ?history=true`, `POST` with `{conversation_id, message, customer_email, customer_name, greeting}`), but instead of calling OpenAI/tools itself, it opens an internal request to a FastAPI `POST /internal/chat` (streaming) and re-emits the same SSE frames byte-for-byte to the storefront. Auth between Node and FastAPI: a shared internal secret header (new env var, e.g. `INTERNAL_API_SECRET`) since this is a private service-to-service hop, not customer-facing.

`preview_ready` payloads (recommendationId, previewUrl) keep flowing through unchanged since the preview page and Save Build/Add to Cart stay on the Node/Shopify side and only need the recommendation ID to look up `FragranceRecommendation` — which FastAPI already wrote to the shared DB.

## 6. SSE compatibility strategy

Confirmed real event types actually emitted today (grepped, not inferred from doc comments): `id`, `profile_progress`, `preview_ready`, `chunk`, `message_complete`, `end_turn`, `error`. **The architecture doc's own comment lists additional events (`analysis_progress`, `candidate_products`, `combination_recommendations`, `recommendation_refined`, `recommendation_confirmed`) that were not found actually emitted anywhere in the code read** — treat that list as aspirational/stale, not a contract to preserve byte-for-byte. ## 8. Risky dependencies / behavior to preserve — key findings

- **Scoring constants are split across three files, not cleanly contained in `fragranceScoring.js` as the request implied.** `fragranceScoring.js` only holds `SCORE_WEIGHTS`, `classifyDislikeConflict`, `matchedLikes`, `computeEvidenceLevel`. Exact-note coverage tiers, family-breadth bonus, compatibility pairs, and risk penalties live in `fragranceCompatibility.js`. Complexity penalty, balance scoring, `TYPE_SIMPLICITY_SCORE`, and the full confidence state machine + breakdown live in `recommendationEngine.server.js`. Port order must treat all three as one scoring surface, or parity tests will pass per-file while failing end-to-end.
- **`combinationAnalysis.server.js` is NOT the combination generator.** It's a 110-line read-only `ExistingCombination` lookup module. Generation/anchor-selection/ratio/dedup logic is entirely in `recommendationEngine.server.js`, and the auto-select walk (eligibility → Odoo → confirm) is in `fragranceAgentTools.server.js`. Scope this correctly in the work breakdown so the engine port isn't underestimated.
- **Exact-note vs family-dislike split** (`splitDislikesByExactness`) is the mechanism that stops "I dislike Sandalwood" from silently hard-rejecting every Cedar/Vetiver product via family-level collapse — this was a documented bug fix; the Python port must replicate the whole-word/`FAMILY_DESCRIPTOR_WORDS` distinction exactly, not simplify to substring matching.
- **Odoo insufficient-vs-unknown semantics** are a specific three-way branch (`CONNECTED`+short → confirmed insufficient; `MISSING`/`SKU_NOT_FOUND`/`LOOKUP_FAILED` → excluded from the insufficiency calc entirely, `inventoryValidated=false`). A naive "if not enough stock, reject" port would break the documented WARN semantics and the `autoConfirmConfidence` tests specifically guard against that.
- **`TYPE_SIMPLICITY_SCORE` biases every customer toward Hybrid by default** (fixing a prior "everything comes back Quadbrid" bug) — this is exactly the kind of tuning constant that's easy to "improve away" during a rewrite; port the literal values.
- **OpenAI model/temperature are hardcoded string literals today**, not env-driven (`gpt-5.4-mini`/`temp 0.3` in chat.jsx, `gpt-4.1-mini`/`temp 0.5` in copy generation), contradicting the architecture doc (which says `gpt-4.1-mini` for conversation). The Python port should follow the *task's* instruction (env-driven `OPENAI_MODEL`/`OPENAI_TEMPERATURE`) rather than the current hardcoded values, defaulting to whatever the live chat model currently is (`gpt-5.4-mini`) so behavior doesn't silently change on migration — confirm this default with the team before shipping.
- **`ProductRegionSummary` is a precomputed, offline-built aggregation table** (`scripts/build-region-summary.cjs`), not something Python should ever compute live from the 936k-row `OrderHistory` table — city tier alone stays live (`groupBy`, small per-city row counts).
- **Copy-generation guardrails differ per violation type**: an unearned-exact-note violation is never retried (no safe way to avoid repeating the false claim), but an unmatched-family violation gets exactly one retry with the missing-families list injected — do not unify these into one generic retry loop.
